# F006: Schedule and cancel notification series (64-cap aware)

## Goal
Saving, editing or deleting an appointment keeps the device's local notifications in sync with
`buildSeries` + `withLines`. Only the next 2 in-person events get a series (the iOS 64 cap), and the schedule
is topped up when the app comes to the foreground (harness/feature_list.json F006; PLAN "Platform constraints").

## Approach (layers per docs/ARCHITECTURE.md)
As built after fix round 2; the reasons are in Decisions.
- **domain/notificationPlan.ts** (pure, `now` injected):
  - `planNotifications(appointments, now, justSaved?, limits?) → { notifications, skipped }`.
    Each notification is `{ key, appointmentId, step, at, title, body }`, with
    `key = "series:<appointmentId>:<step>"` (`notificationKey` / `parseSeriesKey`). An appointment whose
    series throws is reported in `skipped`, not planned.
  - `diffSchedule(planned, scheduled, { now, keepImminentFor }) → { toCancel: ids[], toSchedule: planned[] }`.
    Only identifiers in the `series:` namespace are touched. One is kept only when key, `at` and body all
    match (or it is imminent for an unchanged appointment); anything changed is cancelled and scheduled again.
  - `timingChanged(before, after)`: whether an edit re-times the series.
  - Policy:
    - Only active appointments (`isActive`).
    - The next **2** in-person appointments that still have steps get their full remaining series.
    - The next **20** appointments that aren't in person get their single polite reminder.
    - Hard cap: **60** planned in total, leaving margin under iOS's 64; the soonest win.
    - A due step (`at <= now`, the F003 pull-forward) is planned only for an appointment just added or
      re-timed, at `now + 5 s`; every time is rounded up to a whole second.
- **services/**: a small port (`notificationsPort.ts`) over `expo-notifications`.
  - `setup()` (Android channel "nag", high importance, created once), `getPermission()`,
    `requestPermission()`, `listScheduled() → { id, at, body }[]` (id = OS identifier; `at` from an Android
    DATE trigger, else `content.data.at`), `schedule(planned) → id` (DATE trigger, `identifier: key`),
    `cancel(id)`.
  - `notifications.ts` loads only `expo-notifications/build/<file>` modules through a guarded loader that
    runs once during module evaluation and also registers `setNotificationHandler`; if loading fails, the
    port is a no-op reporting `unavailable`. The architecture checker restricts and traces these imports.
  - `notifications.web.ts` is a no-op adapter (`unavailable`): web has no local notifications, and the app
    stays usable (PRINCIPLES #5). `notificationsFake.ts` is the in-memory port for tests.
- **state/scheduler.ts**: `ensurePermission(port, ask)`, `nextPermission(previous, read)`,
  `syncNotifications(port, appointments, now, justSaved?)` (list → plan → diff → cancel → schedule), and
  `createSyncQueue` (one run at a time; requests made mid-run merge into one follow-up).
  - The store's `syncNotifications(savedId?)` runs after hydrate, after every add/update/remove, and on
    `AppState` → active (`useForegroundSync`, wired in `app/_layout.tsx`); ui/ never touches services.
- **Permissions**:
  - Ask on the first add or re-time, not on launch.
  - If permission is denied, Home shows a small non-blocking banner: "Notifications are off. Nag can’t reach
    you." (PLAN: usable with notifications disabled). `denied` stays shown until a read says otherwise than
    `undetermined` (fix round 2).
- **Notification content**:
  - The title is "Nag"; the body is the `withLines` text (it already carries the cue); data is `{ at }`.
  - The "I've left" action is F007 and out of scope.

## Decisions
- **Source of truth for what's scheduled** (2026-09-25): the OS list (`getAllScheduledNotificationsAsync`), matched by identifier (`series:<id>:<step>` since fix round 1; originally `data.key`). We don't use `Appointment.notificationIds`, because the stored ids can drift from the OS after a reinstall or an OS-side clear. Reconciling against the OS list is idempotent. The field stays in the type for now, always `[]`. Update the PLAN Core model comment and log it in tech-debt (remove it with the next storage migration).
- **2 in-person series**: PLAN says "~2". A constant `IN_PERSON_SERIES_LIMIT = 2`.
- **Foreground top-up**: via `AppState`. Background fetch is out of scope, as PLAN says "later".
- **Web**: the no-op adapter, and the banner is hidden on web (it's never a notification platform).
- **Clock**: sync takes `now` from the injected Clock (src/state/clock.ts). There are no real-clock reads outside clock.ts (architecture check).
- Install with `EXPO_OFFLINE=1 npx expo install expo-notifications` (the sandbox blocks api.expo.dev).
- **Due steps only on a save** (2026-09-25, implementer): `buildSeries` pulls the latest passed step to `now`
  on every call while `now < startsAt`, and the OS drops a notification once delivered, so a plain reconcile
  would re-schedule an already-fired step on every foreground. `planNotifications(appointments, now, justSaved)`
  therefore plans a due step (`at <= now`) only for appointments just added or re-timed (fix round 1:
  an update counts only when startsAt, travel, buffer or in-person changed, via `timingChanged`, so a
  title- or intensity-only edit never re-fires); on other syncs only future steps are planned. Every planned time is clamped to at least `now + FIRE_NOW_LEAD_MS` (5 s), in
  the domain, so the service stays a plain DATE trigger with no time logic (PRINCIPLES #6).
  - Consequence: re-timing an appointment mid-series re-fires its current (pulled) step once, with the
    current cue. Logged in tech-debt.
  - An in-person appointment whose only remaining step is due (and not just saved) doesn't take one of the
    2 slots, so the next one gets its series.
- **Imminent notifications survive a later sync** (2026-09-25, implementer): a save schedules its due step
  5 s out; a sync a moment later (e.g. the iOS permission dialog makes `AppState` go inactive → active) no
  longer plans it. `diffSchedule(planned, scheduled, { now, keepImminentFor })` leaves an unplanned entry alone
  when it fires within `FIRE_NOW_LEAD_MS` and its appointment is active and wasn't just saved. Deleted or
  just-edited appointments still get it cancelled or replaced.
- **Plan limits are a parameter** (2026-09-25, implementer): with 2 × 6 + 20 = 32, the 60 cap can't trigger
  with today's constants. `planNotifications` takes an optional `limits` (default: the constants) so the cap
  and "soonest win" are tested.
- **Port shape** (2026-09-25, implementer): the port is `setup / getPermission / requestPermission /
  listScheduled / schedule / cancel` (`src/services/notificationsPort.ts`). `setup()` replaces `ensureChannel()`
  (creates the channel once); it runs before the permission read because Android 13+ needs a channel before
  the prompt. `setNotificationHandler` (banner + list + sound, so nags show while the app is open) is
  registered when the adapter loads (fix round 1). Permission is `granted | undetermined | denied |
  unavailable`; web, or a failed native load, returns `unavailable` (no banner, no work). iOS
  provisional/ephemeral count as granted.
- **Sync wiring** (2026-09-25, implementer): the store owns `syncNotifications(savedId?)` (never rejects; logs
  with `console.warn`) backed by `createSyncQueue` in `state/scheduler.ts`: one run at a time, requests made
  mid-run merge into one follow-up (their saved ids together). A run hydrates first and does nothing after
  a failed load (an empty list must not cancel everything), then reads permission (asking only when the run
  includes a save and the user was never asked), then reads state and the clock (after any prompt), then
  reconciles. Individual cancel/schedule failures are collected and logged; the rest go through. Saves
  never await it. Foreground top-up: `useForegroundSync()` (state/) in `app/_layout.tsx`.
- **Tests without services in ui/** (2026-09-25, implementer): `resetAppointmentsForTests(clock, notifications)`
  now needs a port; ui tests get the in-memory fake through `src/state/testing.ts` (a re-export), since ui/
  may not import services/. `jest.setup.ts` mocks `expo-notifications` globally so no test touches native code.
- **Banner copy** (2026-09-25, implementer): "Notifications are off. Nag can’t reach you." in a bordered
  surface box (`rounded-button border-line bg-surface`, `text-label text-ink-muted`), above the load error.
  Not in the Stitch export; kept neutral (no tone colour) because it is status, not a nag.
- **Fix round 1** (2026-09-25, reviewer findings):
  - **Deep imports, lazy and guarded:** the package root's `DevicePushTokenAutoRegistration.fx` calls
    `addPushTokenListener` → `warnOfExpoGoPushUsage`, which throws on Android in Expo Go. The adapter now
    `require`s only `expo-notifications/build/<file>` modules (scheduleNotificationAsync,
    cancelScheduledNotificationAsync, getAllScheduledNotificationsAsync, NotificationPermissions,
    NotificationsHandler, setNotificationChannelAsync, and the three `.types` modules for enums) inside a
    try/catch, once, at module load; on failure the port is a no-op reporting `unavailable`, with one
    `console.warn`. The architecture checker restricts imports to that file and those paths and traces each
    one's require graph (none reaches `build/index.js` or a `.fx` module). Type imports use the same deep
    paths. Fragility logged in tech-debt.
  - **Permission mapping:** not granted + `canAskAgain` → `undetermined` (Android 13+ reports
    `denied`/`canAskAgain: true` before the first prompt); not granted + `!canAskAgain` → `denied`. Right after
    asking, anything but `granted`/`unavailable` counts as `denied` (so the banner shows after a no, even
    while Android would allow asking once more; the next add or re-time asks again).
  - **Identifiers:** the OS identifier is the key (`identifier: planned.key`), and listing reads the key from
    `request.identifier`, never from data. `at` comes from the trigger when it is an absolute Android DATE
    trigger (`{ type: 'date', value }`); iOS turns a DATE trigger into a relative
    `UNTimeIntervalNotificationTrigger` (`{ type: 'timeInterval', seconds }`), so there `at` comes from
    `content.data.at`. Neither → unknown (invalid Date) → the diff reschedules it. Planned times are rounded up
    to a whole second (iOS truncates the timestamp to seconds).
  - **Namespace:** keys are `series:<appointmentId>:<step>`; `diffSchedule` ignores any identifier that
    doesn't parse as a series key. **Note for F007:** give snooze/roast notifications their own prefix
    (e.g. `snooze:`), never `series:`, and cancel them yourself; the series sync will not touch them. A
    supportive series that *replaces* the ladder should instead change what `planNotifications` plans.
  - **Bad data:** `planNotifications` returns `{ notifications, skipped }`; an appointment whose series throws
    is skipped (its old series entries are cancelled as unplanned) and logged by the store; the rest sync.
  - **Exact alarms:** expo-notifications uses exact alarms only when `canScheduleExactAlarms()`. app.json
    declares `SCHEDULE_EXACT_ALARM` for dev builds; Expo Go ignores app.json permissions, so this is harmless
    there. `USE_EXACT_ALARM` was not used (Play policy limits it to alarm/calendar apps). PLAN "Platform
    constraints" states the Expo Go consequence; the Android 14 settings prompt is logged for the dev-build
    milestone.
- **Fix round 2** (2026-09-25):
  - **Sticky `denied`, in memory:** on Android 13+ the permission dialog pauses the activity; when it closes,
    `AppState` → active runs a sync that doesn't ask, and the read says `undetermined` again (denied +
    canAskAgain), which hid the banner. `nextPermission(previous, read)` keeps `denied` when the next read is
    `undetermined`; any other read (e.g. `granted` after the user enables notifications in Settings) replaces
    it. Chosen over persisting an "asked" flag because it needs no storage and no migration; consequence:
    after an app restart the banner stays hidden until the next add or re-time asks again (Android shows
    the dialog once more, then `canAskAgain` goes false and reads say `denied` for good).
  - **Loader placement:** the deep requires must stay nested in `notifications.ts`'s own module evaluation;
    a note in the code explains that Metro treats a later native-module throw as fatal.
  - **Checker trace:** a relative dependency that resolves to no file now fails the check (directory imports
    resolve to `index.*`; explicit extensions such as `.cjs` resolve as written), and dynamic `import()` is
    followed. Probed in a scratch copy of the repo layout, not in the repo.
- No `expo-notifications` config plugin in app.json: `expo install` didn't add one and it only sets
  icon/colour/sounds for builds; Expo Go ignores it.

## Verify
- Saving an in-person appointment schedules its series; editing reschedules; deleting cancels
- Only the next 2 in-person appointments have series scheduled; top-up on app foreground
- Unit tests for scheduling policy with a fake notifications service
- Manual: event 2 min out on a real phone via Expo Go produces escalating notifications
- bash scripts/check.sh passes
- Extra tests:
  - Plan: the cap of 60; the soonest win; not-in-person reminders included; inactive appointments excluded; a clamped step.
  - Diff: unchanged → no-op; an edited time or text → cancel + schedule.
  - Sync: serialised, including a concurrent trigger.
  - Foreground top-up: after the first event passes, the third in-person event gets scheduled.
  - Permission denied → no schedule calls and the banner shows.
